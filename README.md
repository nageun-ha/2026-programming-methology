# Git 협업 규칙

## 1. 회의 규칙

- **월/화 중 하루**: 20분 내외 스탠드업
  - 지난 회의 이후 한 일 / 앞으로 할 일 / 막힌 점만 공유
  - 길어질 이야기는 목요일 회의 안건으로 넘기기
- **목요일**: 장시간 정기 회의
  - 코드 리뷰 결과 공유, 설계 논의, 다음 주 작업 분배
  - 수요일까지 논의할 안건을 이슈나 단체방에 미리 올리기

## 2. 브랜치 전략

- `main`: 항상 빌드가 통과하는 상태 유지, **직접 push 금지**
- `develop`(선택): 팀원이 많을 때 통합용으로 사용
- 작업 브랜치는 `main`(또는 `develop`)에서 분기

브랜치 이름 규칙:

- `feature/기능-이름` (예: `feature/login-screen`)
- `fix/버그-내용` (예: `fix/crash-on-start`)
- `refactor/대상` (예: `refactor/network-module`)
- `docs/문서-내용` (예: `docs/readme-update`)
- `hotfix/긴급-내용`
- `chore/잡일

## 3. 커밋 메시지 규칙

형식: `타입: 한 줄 요약`

| 타입 | 의미 |
|---|---|
| feat | 새 기능 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 코드 개선 |
| style | 포맷 등 로직과 무관한 수정 |
| docs | 문서 수정 |
| chore | 빌드 설정, 의존성 등 |

- 예: `feat: 로그인 화면 UI 추가`
- 커밋은 작은 단위로, 한 커밋에는 한 가지 목적만 담기

## 4. PR 규칙

- 작업 브랜치 → `main`(또는 `develop`)으로 PR 생성
- **최소 1명 이상 승인 후 머지** (본인 PR은 본인이 머지하지 않기)
- PR 설명에 작업 내용, 관련 이슈 번호, 확인 방법(스크린샷 권장) 작성
- PR은 가급적 작게 유지(수정한 줄 150줄 이하. 커밋 갯수는 5개)
- 머지 방식: 3-way-merge
- 리뷰 기한: PR 생성 후 48시간 이내 (목요일 회의 전 리뷰 완료가 목표)
- PR에서 의존성과 관련된 모두가 리뷰 책임이 있음.

## 5. 안드로이드 프로젝트 규칙

- `.gitignore`에 `local.properties`, `build/`, `.idea/`, `*.iml`, `.gradle/` 포함
- API 키, 키스토어 파일은 **절대 커밋 금지**
- 개인 IDE 설정(`.idea`) 커밋 금지
- 머지 전 로컬에서 빌드 성공 확인
- 코드 스타일: Kotlin 공식 컨벤션 + Android Studio 기본 포맷(Ctrl+Alt+L)
- 충돌이 잦은 파일(`build.gradle`, `AndroidManifest.xml`, 레이아웃 XML)은 수정 전에 팀에 공유

## 6. 이슈 관리

- 작업 시작 전 GitHub Issues에 등록하고 담당자 지정
- 라벨: `feature`, `bug`, `question`, `urgent`
- PR 설명에 `Closes #이슈번호` 작성해 자동 연결
- GitHub Projects 칸반(To do / In progress / Review / Done)으로 진행 상황 공유

## 7. 주간 운영 흐름

| 요일 | 할 일 |
|---|---|
| 월 | 20분 스탠드업, 이번 주 작업 확인 |
| 목 | 장시간 회의: 리뷰 마무리, 설계 논의, 다음 주 작업 분배, pr 남는 것 없도록 |

## 8. 충돌·긴급 상황

- 작업 시작 전 항상 `git pull`로 최신 상태 확인
- 충돌 발생 시 해당 파일 작성자와 바로 상의
- 긴급 버그는 `hotfix/` 브랜치로 빠르게 PR → 리뷰 후 머지
